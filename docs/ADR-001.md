# ADR-001 — Windows local application and integration boundaries

Date: 2026-11-03 (Pacific/Auckland). Status: **desktop application direction approved by owner; concrete dependencies, authentication and release feasibility remain to be validated**.

## Options and recommendation

| Option | Daily use and release | Main tradeoff | Assessment |
| --- | --- | --- | --- |
| Local Node web server + browser | Small dependency footprint; script can open browser | Server lifecycle, runtime distribution, port access and updating need extra work | Good disposable Phase 0 spike |
| Electron + TypeScript/React + SQLite | Bundled runtime, desktop shortcut, established Windows packaging/update tooling | Larger download/memory footprint; IPC and signing require care | Recommended product direction |
| Tauri + TypeScript/React + SQLite | Smaller desktop bundle; established desktop tooling | Adds Rust/native Windows prerequisites and sidecar integration | Viable; no Rust toolchain found on this machine |
| .NET WPF + SQLite | Native Windows UI and self-contained distribution possible | Different UI stack; Node SDK integration becomes a sidecar | Viable; dotnet host found but no SDK listed |

These are engineering judgments, not measured performance claims. Electron was not installed or packaged during this spike. A real packaged two-version test is required before committing to its updater.

## Proposed product boundaries

- Renderer: task UI and review conversation, TypeScript/React, no Node integration. Main process: validated IPC, persistence, process lifecycle, credential access and GitHub adapter. Use context isolation/sandboxing and a narrow preload API; reject navigation and arbitrary shell commands from untrusted rendered content.
- SQLite: versioned transactional migrations, foreign keys, WAL and online backup. Stable release data path proposed as `%LOCALAPPDATA%\FocusFlow\data\tracker.db`, independent of app version/install path. The spike currently uses `.phase0/data/phase0.db`; no real tasks will be silently imported.
- Choose a maintained SQLite driver against the pinned Electron runtime in the packaging spike. Node 24.12.0's experimental `node:sqlite` API used here must not be assumed available in Electron. Rebuild/packaging compatibility for native drivers is also unverified.
- Codex adapter: a separately launched official `codex app-server` over stdio, protocol bindings generated for the pinned tested CLI version; one active coding run globally for MVP. Model runner stays replaceable. The local App's internal alpha executable proves handshake feasibility only; require an explicitly selected supported CLI distribution before production use.
- Execution isolation: per-run Git worktree under a separate run directory, restricted working directory/sandbox, approval prompts surfaced in UI, explicit interruption and timeout handling. A worktree alone is not a security sandbox. No blanket inherited GitHub token/model credentials in run logs or renderers; minimal environment. No direct control over existing user sessions.
- Failure recovery: durable run/step IDs and Codex thread/turn IDs, progress events, reconnect/reconcile on restart. Interrupted process, approval waiting, quota exhaustion and failed tests are execution substates, not new implicit starts or successful completion.

## GitHub ownership and synchronization proposal

| Data | Authority | Behavior |
| --- | --- | --- |
| Personal tasks/history | Local database | Never publish to GitHub |
| Project tree, local Ticket ID, acceptance, dependencies | Local database | User-approved coding Ticket projection to Issue only |
| Issue number/URL, PR number/head SHA, checks and merge result | GitHub | Persist observed remote facts; refresh on focus and explicit request |
| Issue title/body changed remotely | Conflict requiring review | Flag drift; never silently overwrite either version |
| Coding Ticket Done | Observed linked PR `merged_at`/merge state | Issue closed or PR closed-unmerged never marks Done |

Local approved writes use an outbox record with a stable Ticket UUID in the published Issue marker. Reconcile ambiguous API timeout results before retrying creation to avoid duplicate Issues/PRs. PR branch names include the Ticket ID. Do not try to make a local SQLite transaction and a remote API write atomic. Retries must be visible and resumable.

For MVP merge is proposed via the GitHub PR page; Tracker refreshes and checks actual merge status. This keeps branch protections/check policies under GitHub. In-app merge can later require explicit approval bound to the current head SHA; changes invalidate old review approval.

Product authorization candidate: GitHub CLI device/browser login with selected repository permissions, managed by GitHub CLI/OS credential storage. `gh` is not currently on PATH. App-based OAuth is another option if CLI deployment proves too awkward; not yet selected. The development assistant's connected GitHub app is verified against the owner and repository, but that does not supply authorization to the future Tracker executable. Do not ask the user to paste a token into chat. Issue creation needs Issues write; branches/code push need Contents write; PR creation needs Pull requests write. Repository creation authorization is a separate bootstrap concern and must not be silently bundled into runtime scope. Public read access does not prove any of these write permissions.

## Review evidence proposal

Persist base/head commit SHA, actual diff, changed file list and dependency manifests, runner command/cwd/exit status, test output artifact and CI check results with their SHA. The first panel says what changed, what was checked, and what is uncertain. Label facts as test execution / code observation / AI inference / not checked. A developer summary is a claim, not verification.

An independent reviewer gets a fresh context containing acceptance criteria and real diff/evidence. This reduces shared conversational assumptions but does not make AI review infallible. Materialize remote PRs in a controlled worktree, do not run untrusted test commands with account tokens. Missing/truncated diffs, failed tests and stale SHA must remain visible. Natural-language requested changes resume the same Ticket/PR and invalidate review evidence when code changes.

## Update and recovery proposal

Use maintained Electron packaging: NSIS installer + electron-updater + GitHub Releases as a candidate, never `git pull` as an end-user update mechanism. Pin versions after a packaging spike because signing/update behavior varies by tool version. Check Windows Authenticode and signed-manifest requirements and any certificate costs before promising a frictionless public installer. Do not silently disable verification to make a demo pass.

User explicitly chooses download/install/restart of a formal release. Stop active coding runs and database writes, take an online consistent backup, verify it, record source app/schema version, close database, then install/restart. Migrations run transactionally after retaining the old snapshot. If startup/migration fails, preserve the failed database separately and offer an offline recovery with a compatible previous binary and snapshot. A previous binary must refuse a newer database schema. Binary rollback, restore UI, disk-full handling, installer interruptions, and a real version A→B update with existing data are all still unverified.
